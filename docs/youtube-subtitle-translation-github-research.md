# YouTube / 在线视频字幕翻译开源方案研究> 调研日期：2026-08-13> 范围：只阅读 GitHub README、源码与提交历史；未修改 EchoSub App。> 目的：回答“逐句翻译是否应携带视频全文概括”，并找出值得 EchoSub 借鉴的真实实现。## 结论先行**建议把“视频全文概括”加入背景卡，但不要把它当成唯一上下文。** 更稳的组合是：1. 用完整字幕做一次翻译前分析，生成有长度上限、带证据位置的背景卡；2. 实际翻译仍按一批 20–40 个字幕句处理，并携带前后各 3–5 句原文；3. 每批都携带同一份静态背景卡：全文概括、分段大纲、人物/机构、术语表、语气和疑点；4. 当前原句与相邻原文是“硬证据”，背景卡只是“软提示”，二者冲突时必须服从原文；5. 用编号严格校验“每句都有译文且不串位”，只补翻失败句簇，不因一处漏翻重跑全文。这会比“每 4 句孤立翻译”明显更利于处理指代、术语、说话人口吻和跨段主题。即使按用户提供的前提，DeepSeek v4 Flash、Qwen 3.7 Plus / Flash 都有 1M 上下文，也**不建议每一个翻译批次重复附上整份字幕**：这会放大输入成本、延迟和无关信息干扰。1M 上下文更适合保证“翻译前的全文分析真正覆盖全文”，而不是取消分批和验证。一个重要警告来自 LLM-Subtrans：它允许给影片 description，但 README 明确写道说明应简短，太多背景会让 AI 开始自行发挥（“Less is generally more … AI can start improvising”）。因此，背景卡必须短、结构化、可追溯，而不是一篇长篇故事梗概。[LLM-Subtrans README](https://github.com/machinewrapped/llm-subtrans/blob/084a574f40097957030001e4e6a6b99656c37bae/readme.md#L276-L293)## 两类项目不能混为一谈| 类型 | 00:00-03:20: 本段主题一句话  - 03:20-08:40: 本段主题一句话domain: 领域、受众、视频类型tone: 正式/口语/教程/访谈，以及主要说话人口吻entities:  - source: Julian Treasure    preferred_zh: 朱利安·特雷热    evidence: [cue_12, cue_98]terminology:  - source: controls    preferred_zh: 控件    do_not_translate: false    evidence: [cue_215, cue_230]uncertainties:  - cue_342: ASR 可能把专有名词听错```### “全文”应如何保证- 分析请求的输入必须是**完整字幕**，每句带稳定 cue ID/时间戳；不能像 VideoLingo/KISS/LattifAI 那样只取开头 8,000 或 50,000 字符，却在 UI 上称作全文概括。- 既然用户常用的 API 按其说明支持 1M 上下文，普通 YouTube 字幕可先尝试单次全文分析。若实际 API、网关或输出限制不允许，则用“按时间分段概括 → 汇总所有分段概括”的层级方式，但仍要保证每个 cue 至少被某个分析块覆盖。- `overview` 应有明确长度上限，例如 800–1500 个中文字；背景卡整体建议约 1.5k–3k tokens。模型上下文大，不代表背景越长越好。- 每个实体/术语/不确定点应带 evidence cue IDs。找不到证据的内容不进入卡片。- 背景卡生成失败不阻止视频播放；降级为“局部上下文翻译”，之后允许用户手动重试生成卡片。### 每个翻译批次建议携带什么1. 精简后的完整背景卡；2. 本批 20–40 个有编号的目标 cue；3. 本批之前 3–5 个、之后 3–5 个只读上下文 cue；4. 仅筛选出会在本批/邻句出现的术语，而不是整张大术语表；5. 约束：“不得依据概括补写源文没有的信息；概括与原句冲突时服从原句；每个编号恰好输出一个翻译”。### 并发与历史的选择- **第一版建议：静态背景卡 + 静态术语表 + 邻句，并发 2–3 批。** 它可预测、缓存容易、适合 DeepSeek/Qwen。- 若让每批继续生成新的术语/scene summary 并传给下一批，就必须串行，或者按 scene 分 lane 串行；否则历史顺序会像 ViDove 的并行 history 一样不可靠。- 更好的折中是：全文分析阶段一次性生成静态术语表和分段大纲，翻译批次并发；翻完后再全局检查术语和疑似指代，不在翻译中动态改全局状态。## 漏翻、错位和重试的具体建议1. 输出必须是 `{cue_id, translation}` JSON 数组；cue ID 不允许由模型改写。2. 校验缺 ID、重复 ID、额外 ID、空翻译、原文回显和目标语言明显异常。3. 某句漏翻时，右键“补翻/重试”实际发送：目标句 + 同一语义簇 + 前后少量只读上下文 + 背景卡；只写回用户选择的 cue。4. 一批中部分成功时保存成功句，不重翻整批；对失败的连续句簇缩小窗口重试，借鉴 Subtitle Translator。5. 全部重新翻译才清除该视频目标语言的翻译缓存；“补全翻译”只扫描空/失败 cue。6. 缓存 key 至少包含：`video/transcript hash + cue source hash + source/target language + model + prompt version + background-card hash + glossary hash`。7. 429 用共享退避闸；鉴权/无效 key 立即停止；上下文超长时缩小局部窗口，但保留短背景卡。## 建议的小规模 A/B 测试可选 2–3 个包含技术术语、多人对话和跨段指代的视频，每个抽取相同的 100–200 句，盲测三组：- A：每批只带前后邻句；- B：邻句 + 本文建议的完整背景卡；- C：每批附完整原始字幕 + 目标句标记。记录：漏翻率、cue 错位率、术语一致率、指代正确率、人工偏好、首屏等待、总 token 和费用。预期 B 最可能取得质量/成本/稳定性的平衡；C 虽使用 1M 上下文，未必比 B 更准确，而且每批重复输入全文的成本和延迟最差。最终仍应以你实际使用的 DeepSeek v4 Flash、Qwen 3.7 Plus / Flash 结果为准。## 最终产品判断- **“翻译前做全文概括，然后每句翻译携带概括”方向是对的。**- 但产品实现应叫“全文分析背景卡”，不只是一条 summary；至少同时有分段大纲、术语、实体、语气和疑点。- 背景卡中保留用户要求的“视频全文概括”，但要短、可编辑、有证据，并明确低于原句和邻句的权威级别。- EchoSub 的默认翻译单位应从极小的 4 句提升到约 20–40 cue 的语义批次，再附前后 3–5 句。具体值做成可调，不要仅按 1M 上下文把批次无限放大。- YouTube 获取继续优先 yt-dlp/原生 timedtext；翻译质量层应参考 LLM-Subtrans、VideoLingo、LattifAI 和 Subtitle Translator，而不是只参考逐 cue 的实时 Google 翻译插件。
